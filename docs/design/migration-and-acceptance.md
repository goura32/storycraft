# 移行方針と受入確認の設計

## 1. 移行方針

V1 は旧設計との互換層を持ちません。旧 `run-state`、巻引継ぎ、完結結果、シリーズ一括公開を通常実行時に読み替えたり、自動変換したりしません。

新形式は `run-state.schema_version = 3` の新規作業場所で開始します。run-state の保存形式の唯一の正本は [状態と遷移](state-and-transitions.md) です。既存の作業場所を静かに変換してはなりません。V1 は移行操作を提供しません。

## 2. 受入確認

試験は設計を探索する道具ではありません。以下の受入契約を、決定的模擬 Ollama で確認します。詳細な検証器ごとの網羅的な試験用資料増殖は行わず、既存の受入契約で再現できない実障害を追加した場合だけ回帰確認を追加します。

| 受入契約 | 確認すること |
|---|---|
| 4巻の通常完走 | 各巻が公開済みになってから次巻計画へ進み、最終巻公開で `completed` になる |
| 非最終巻公開 | 当該巻だけの原稿・公開記録ができ、全巻原稿・完結結果・引継ぎがない |
| 全巻の巻公開 | 各巻が同じ公開基準で確定し、最終巻の公開後にだけ `completed` になる |
| 形式不正上限 | シードが重複せず、生成・確認で `invalid_response_limit` 回すべてが形式不正なら採用・公開・次工程へ進まない。修正中に既存の形式有効候補がある `quality_revision_limit=0` の例外は注意付き採用する |
| 品質修正上限 | 形式有効な修正を上限まで行って重大指摘が残った場合、最後の構造有効版を編集上の注意付きで採用し、通常工程は進む。修正応答の形式不正上限は別契約で判定する |
| 公開途中の中断 | `run` が健全な manifest の target を収束し、提供者呼出しや二重公開を増やさない |
| 公開済み不変性 | 公開済み巻と構成元の採用参照の変更を拒否する |
| 不整合停止 | 参照・確定物の不整合を検出したら `blocked` のまま停止し、通常操作で再開しない |
| CLI 到達性 | 隔離した schema version `3` 作業場所で `init`、`run`、`status`、`validate` を子プロセスで通し、確定途中の収束・検証では提供者を初期化しない |

Ollama 実機は、自動試験とは別に、新規作業場所で CLI 受入表の経路を通すスモーク確認として扱います。実機確認は、共有指示文・スキーマ・LLM 境界を変更した後だけ実施し、生の依頼/応答を確認してから評価します。CLI 受入は模擬 Ollama を明示設定して子プロセスで実行し、公開サービスの直呼びだけを根拠にしません。

## 3. 完了条件

V1受入の完了は、旧テストが緑になることではありません。次を満たしたときです。

1. 新規 schema version `3` 作業場所で、受入表に定めた契約が通る。
2. 公開経路・作業場所検証器・CLI 振分けに旧引継ぎ/完了処理/シリーズ公開の到達可能な参照がない。
3. `validate` が提供者なしで正本参照、確定状態、公開不変性、LLM 記録連鎖を検証する。
4. 最後の共有設計・指示文・スキーマ変更後に、新規作業場所で CLI 受入表の経路を使った実機 Ollama スモークが通る。
5. 旧実装・旧試験用資料・旧試験を、互換層なしで削除または新設計へ置換する。
