# 初期設計工程の契約

## 1. 単位と責務

`initial_design` は、作品の構造と意図を一つの候補として生成、確認、必要なら修正し、採用する工程です。人物だけ、世界だけ、結末だけを別工程で確定しません。人物変更後に古い人物像を前提とした関係・設定・結末を残さないためです。

この工程は、採用済み初期設計と、それに対応する最初の作品状態を不変確定します。候補、確認、修正記録は補助成果物であり、作品正本ではありません。

## 2. 入力

| 種別 | 必須入力 | 正本 | 用途 |
|---|---|---|---|
| 正式依頼 | `request_id`、題名、ジャンル、前提、必須要素、避ける条件、結末の希望、巻数、言語 | 採用済み依頼文 | 作品制約 |
| 工程設定 | `settings_id`、スキーマ版、初期設計の品質修正上限、Ollama モデル設定 | 不変設定 | 生成・確認の制御 |
| 改稿時だけ | 現候補全体、対象確認記録の有効な重大指摘全体 | 候補・確認記録 | 全体修正 |

新規作品は依頼文またはキーワードの正確に一方から始めます。キーワード起点では、形式検証と独立確認を通過した依頼文を不変確定し、その `request_id` を入力にします。キーワードそのものや未採用の依頼候補は初期設計へ渡しません。

初期設計は、過去の作品成果物、固定パス上の最新成果物、外部情報を入力にしません。確認には正式依頼と確認対象候補全体を、改稿には正式依頼・現候補全体・有効な重大指摘全体を渡します。

## 3. 出力

### 3.1 候補

形式有効な候補は `initial-design` スキーマとし、次の構造・意図だけを持ちます。

| 項目 | 内容 |
|---|---|
| `core` | 作品の核、主題、読者への約束 |
| `cast` | 人物の名前、役割、関係。LLM は新規人物 ID を返さず、コードが採番する |
| `world` | 世界、制度、制約 |
| `knowledge_model` | 作者、人物、読者の知識構造 |
| `unresolved_threads` | 種別、結末必須性、説明。LLM は新規未解決事項 ID を返さず、コードが採番する |
| `ending_conditions` | 結末必須事項の達成条件。各条件にコードが `ending_condition_id` を採番する。新規未解決事項への対応は名称・意味内容で解決する |

`initial-design` に作品事実の現在値、人物の現在知識、読者開示済み情報を複写しません。

### 3.2 最初の作品状態

候補から別の `generation` スキーマを作り、これを最初の正規形現在状態とします。

| 項目 | 内容 |
|---|---|
| `story_facts` | 初期時点で確定している作品事実 |
| `character_knowledge` | 人物 ID ごとの現在知識 |
| `reader_disclosures` | 読者に開示済みの情報 |
| `unresolved_thread_states` | 未解決事項 ID ごとの現在状態 |
| `timeline_position` | 現在の時系列位置 |

`generation` は initial-design の人物、世界、関係、知識構造、未解決事項 ID と矛盾してはなりません。

### 3.3 確認・修正・採用

- 確認記録: 対象候補 ID、判定、指摘 ID、重要度、根拠位置、説明
- 修正候補: `initial-design` と同一の完全スキーマ。元候補 ID と確認記録 ID は、システム側の候補記録だけが持つ。
- 採用選択: 採用候補 ID、`initial_design_id`、`generation_id`、品質上限到達時の残存重大指摘と注意根拠

確認記録、修正候補、採用選択は初期設計・作品状態の内容を複写しません。

## 4. 決定的検証

コードは次を検証します。

1. 依頼入力の排他、必須項目、言語が日本語、巻数が 4–10、必須条件と避ける条件の明示矛盾。
2. `cast`、関係、世界要素、知識主体、未解決事項、ending condition の ID 一意性、列挙値、参照実在、参照型。
3. 結末必須未解決事項と `ending_conditions` の一対一対応。非必須未解決事項に達成条件を置かない。
4. `generation` の人物、世界、関係、知識、未解決事項状態が採用対象 initial-design と対応し、現在状態として必要な項目をすべて持つこと。
5. 確認記録の対象候補 ID、重要度列挙値、根拠位置の実在・解決可能性。
6. 修正候補の LLM 応答が完全スキーマを持ち、システム側候補記録が元候補 ID・確認記録 ID を束縛し、採用前に候補全体として再検証されること。
7. 一時保存、initial-design、作品状態、採用選択、後続選択スナップショット、`current_target=series_plan` が一つの原子的確定で更新されること。

## 5. LLM 確認と採用

独立 LLM は、正式依頼と候補全体を照合し、人物・関係・世界・知識・未解決事項・結末条件の物語的整合性、必須要素・避ける条件・結末希望の取り違え、主題と読者への約束、知識モデルの不自然なネタバレを確認します。

重大指摘が上限前にあれば、初期設計候補全体を修正し、再検証・再確認します。上限に達した場合は、最後の形式有効候補を注意付きで採用し、残存重大指摘と注意根拠を採用選択に保存します。部分成果物だけを修正・採用しません。

採用後、後続選択スナップショットは `request`、`settings`、`initial_design`、`current_state`、`initial_design_adoption` の各スロットを持ちます。`series_plan` はこれらの正本を直接読み、次工程専用の要約・引継ぎ文書は作りません。

## 6. 失敗

生成、確認、修正の各応答に、初回を含め固定5回・別シードの形式不正再呼出しを適用します。5回とも不正なら候補・作品状態・スナップショットを確定せず `blocked/manual_review_required` にします。通信失敗、設定不正、内部エラーは共通の復旧契約に従います。
